# OllieOS

Ollie's private personal operating system for tasks and work knowledge, readable and writable by Claude through a built-in MCP server. Spec: `docs/PRD.md`, `docs/DESIGN.md`, `design/screens/`. Plan: `docs/build-plan.md`.

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the API server (port 5000)
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- `pnpm --filter @workspace/api-server run test` — vitest for the AI access rules; rebuilds a throwaway `ollieos_test` database each run, never touches the real one. Shared server/MCP/ingest helpers in `test/harness.ts`
- `pnpm --filter @workspace/scripts run mobile-audit` — phone layout check: opens every page at 360 and 375px as a touch device, fails on sideways scroll or the error screen, reports tap targets under 44px and text fields under 16px (`-- --strict` fails on those too, `-- --only /tasks`, `-- --widths 375`). Needs both dev servers, `DATABASE_URL` and `ALLOWED_EMAIL`; signs in with its own session (removed afterwards), blocks every non-GET API call, skips brief pages unless `-- --include-briefs` (opening one can write it with the model). Report and screenshots in `tmp/mobile-audit/`. Needs Playwright's Chromium (`pnpm --filter @workspace/scripts exec playwright install chromium`) or `CHROMIUM_PATH`
- `pnpm --filter @workspace/scripts run seed-tasks` — seed the 10 starting tasks and their people (runs once per database)
- Required env: `DATABASE_URL`; secrets `ALLOWED_EMAIL` (the only email allowed to sign in; if unset, nobody can), `SESSION_SECRET` (also signs OAuth consent requests), `INBOX_API_KEY` (bearer key for `/api/ingest/*`; ingest answers 503 until it is set)

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5
- DB: PostgreSQL + Drizzle ORM
- Validation: Zod (`zod/v4`), `drizzle-zod`
- API codegen: Orval (from OpenAPI spec)
- Build: esbuild (CJS bundle)

## Where things live

- DB schema: `lib/db/src/schema/` (all PRD tables, full-text `search` columns are generated)
- API contract: `lib/api-spec/openapi.yaml`; server routes in `artifacts/api-server/src/routes`, logic in `src/services`
- Shared dates, labels and quick-add parser: `lib/shared` (all dates go through it, London time)
- Theme: `artifacts/ollieos/src/theme/tokens.css` is the only file with colour values; fonts are self-hosted (`src/theme/fonts.css`, files in `src/assets/fonts`), no Google Fonts
- Pages: every page except Home and Tasks loads on first visit; add a new page to `src/routes.ts` (lazy page and `preloadRoute`) as well as `App.tsx`, and to the mobile audit's route list

## Architecture decisions

- Single user: Replit Auth plus an allowlist. A non-allowlisted login gets no session and lands on `/not-authorised`; `requireOllie` guards every data route (401/403).
- Every write records an `audit_events` row in the same transaction; task history is built from those rows.
- Do next ranking: overdue first, then High by due date, then Medium; undated last; snoozed skipped; Low only when overdue.
- Undo restores the `previous` snapshot stored on the latest audit event (1 hour window). A follow-up triage to the same status (adding a Noise rule, changing the Waiting person) reuses the earlier snapshot, so one Undo goes back to Inbox and removes a rule it created.
- Noise rules only apply to new items at capture time; Restore moves an item from Noise back to Inbox.
- Dropped (Assist Part A) means real but chosen not to do; Noise means it should never have come in and teaches rules. Dropped is closed everywhere: counts, Do next, Waiting on, digest, stale checks, MCP and Ask. Restore works from Noise or Dropped.
- Probably noise: `scheduledWork` part "noise" asks Haiku about unchecked Inbox email and Slack items, using noise rules, hand-moved Noise and kept items as examples. Items hidden from AI are marked checked without a hint. A hint shows only while the task is in the Inbox and not kept; Keep or restoring a hinted item sets it as kept.
- Draft reply (email tasks): reads the Gmail thread plus AI-visible context and rules through the Ask client, writes a `reply_drafts` row, and "Save to Gmail" creates or updates a Gmail draft in that thread. OllieOS never sends email. Tasks hidden from AI answer 409; without a findable thread the draft is copy only.
- Web app loading (mobile plan Part B): `main.tsx` calls `startEarlyLoads` (`src/lib/query-client.ts`) before rendering, which starts the page's code and, for Home and Knowledge, their first queries alongside the sign-in check; keep its query keys identical to the pages' hooks. Queries are fresh for 30 seconds (Home 5, for access requests). `index.html` carries a static copy of the Splash screen so phones draw it before the script runs.
- All task state changes in the web app go through `useTaskActions()` so cache invalidation and Undo toasts stay consistent.
- Every AI read goes through `lib/ai-data` with an `AiScope` (client, actor, live grants). Confidential or aiAccess off means hidden; tasks, decisions and notes with confidential null follow their parent, true always hides, false always shows. Every item handed to an AI writes one `read` audit row, grouped by a batch id.
- Access grants are approved `access_requests` rows that last 1 hour and expire at read time (nothing scheduled). A grant applies only to the requesting client; a project/person/organisation grant also opens children hidden only by inheritance. AI tools always get the same `REQUEST_REPLY`, whether or not the item exists.
- Ask OllieOS is its own AI client (`ai_clients` row, auth internal). Its "Allow for this question" grants the held-back items to Ask only, then re-answers the turn. Ollie's own views use no grants.
- Knowledge writes in the web app go through `useKnowledgeWrite()` (`src/lib/knowledge.ts`), which refreshes every Knowledge query plus the task caches.
- Facts are never edited in place; replacing one supersedes it and keeps the history.
- MCP server at `POST /mcp` (stateless, JSON responses) with OAuth 2.1: discovery at `/.well-known/oauth-protected-resource/mcp` and `/.well-known/oauth-authorization-server`, endpoints under `/api/oauth/*` (dynamic registration, public clients, PKCE S256 only). Consent is the web page `/oauth/consent?req=` behind Ollie's sign-in. Access tokens last 1 hour, refresh tokens 30 days and rotate on use; a failed code or refresh attempt still spends it.
- `src/mcp/` and `src/routes/ingest/` never import the database (boundary test): reads go through `lib/ai-data` (visible items only; hidden ones answer `not_found`), writes through services (`aiWrites` for tasks, promises, activity, calendar and notes; `aiPropose`/`suggestions` for Knowledge). Ingest acts as the "Capture sweep" client with actor `ingest`; the AI log shows the client name.
- Capture dedupes on source + source_ref through the `capture_log` unique index, so the same item sent twice, even at once, makes one task. Noise rules apply only when no status is given and never to meeting items. A confidential item is saved but the reply never names it or returns its id.
- Revoke on a connected tool cuts it off at once (tokens revoked, ingest key refused with 403). Reconnect lets the sweep back in; an OAuth tool must go through consent again. Ask OllieOS cannot be revoked.
- Knowledge Inbox (feature 01): AI never writes facts, decisions, people, organisations or projects directly. MCP tools and `POST /api/ingest/suggestions` create `suggestions`; a match with changes becomes a summary_change, a match with nothing new answers "unchanged". Approving writes the record with `createdBy` set to the proposer and audit actor `ollie`. Tasks, promises, activity, calendar and notes still write directly (build plan 24, 26).
- Stale and conflicting facts (feature 02): facts may carry one of a fixed list of attributes. A second current fact with the same entity and attribute but a different value makes a conflict review; a suggestion in a conflict is resolved only through Conflicts (approve/reject answer 400). Ollie adding a fact with an attribute supersedes the current one. The weekly check runs from the sweep's finish call once Sunday 18:00 has passed (no scheduler). Inbox items carry attribute display labels, not keys.
- Ollie's own person record (`is_self`) is created from the signed-in account and shown as "Your profile".
- Direction (features 04 to 07): a task counts towards its own goal, else its project's goal; "not goal work" drops it from the unlinked list, which only covers this week's set (Now or due this week). MCP goal counts include only AI-visible tasks and never return a confidential goal's target. A cadence with no contact on file is Overdue; a person whose linked projects are all paused or complete is paused. Documents have no grants of their own (confidential null follows their projects). Rules (called playbooks before Part M) with no links apply everywhere; paused ones reach no AI; a product's rules apply on projects and organisations linked to it. AI can only propose documents, rules, playbooks, products and cadences through the Knowledge Inbox; an approved rule starts switched on. Seed goals and rules are created once, guarded by an `app_settings` flag. Playbooks (Part M) are processes with ordered steps; only In use ones reach AI, and a playbook with confidential unset follows its linked projects and products.
- Who's who (Part N): people match on the Slack account, then the main or any other email; Slack accounts are only ever linked by Ollie. Merging moves everything to the person kept and never removes Ollie's own profile. "Who decides" is a `decides_on` relationship from a person to a project, product or organisation (no one named means Ollie). Knowledge Inbox cards carry who said the claim and when; "Same as existing" sets the card to `merged` with `resultType`/`resultId` and counts the existing item as checked. Slack and Gmail checks propose decisions and facts through the same sorter read, never for exchanges with someone hidden from AI.
- Contradictions, context packs and round-up (Part O): new cards are checked against approved items by Haiku (`contradictionJudge`, mock it in tests) and open a `contradiction` fact review; "May be out of date" is computed from pending reviews, never stored. Replaced decisions (`supersededBy`) are filtered at each AI site. Context packs and the round-up's Gmail draft only hold what default-scope AI may see; the round-up page shows everything with locks.
- Preparation (features 03 and 08): briefs and the digest summary are written as the Ask OllieOS client, so they only see AI-visible items; Ollie's pages still show hidden items with a lock. A work meeting gets a brief when it is not personal and has a known attendee, organisation or project. `scheduledWork` runs after each finished sweep and after each OllieOS connector check: briefs for work meetings in the next seven days that have not started (unchanged inputs skip the model), then the digest (first run after 07:40 on a weekday; connector checks wait for 07:40), then clears digests older than 30 days and old calendar rows; each part fails on its own. A brief is also written on open when missing or more than 3 hours old. Granola notes arrive at `POST /api/ingest/meeting-notes`; actions go to the Inbox (dedupe on source_ref), decisions to the Knowledge Inbox. The digest email (07:45) is deferred.
- Ask OllieOS uses Anthropic `claude-sonnet-5-5` through Replit AI Integrations (no own key, billed to Replit credits); structured output via `output_config.format` json_schema, no temperature, forced tool_choice is rejected.

## Product

- Tasks tabs (priority, due date and status change straight from the row or phone card), task detail with history and Draft reply on email tasks, Noise and Dropped tabs with Restore, Stale marker on Backlog.
- Settings: Connectors first (replaces AI access and Capture sweep; old slugs redirect): one card per service with status, last check, Check now and a read-by-OllieOS switch, the timer window, then Claude's stats, access requests, connected tools, the Claude sweep and "What AI looked at". Noise rules with hit counts and on/off switches. Knowledge (shelf life per attribute, Check now). Imports and Export are placeholders (milestone 9).
- Connectors (milestone 8, Part A): OllieOS reads Google Calendar itself through the Replit Google Calendar connector (`@replit/connectors-sdk` `ReplitConnectors().proxy`; the v3 `ConnectorsClient` cannot find the connection). Settings in app_settings `connectors` (`{schedule, readBy}`); runs in `connector_runs`, kept 30 days. A ready service with no choice made moves to OllieOS after its first good check; while OllieOS reads it, Claude's copy is answered `{ignored: true}`. Only `DIRECT_READY` services can be switched to OllieOS (others answer 400). An in-process timer ticks every minute and runs at the chosen interval on weekdays inside the window (default every 30 minutes, 07:00 to 19:00 London), claimed atomically in app_settings so two instances never double-run. Off when NODE_ENV=test or OLLIEOS_CONNECTOR_TIMER=off. This reverses PRD Q32 (no timers); the published app must be always on (Reserved VM) for timed checks. Part B: Gmail (`google-mail`) and Slack (`slack`) are read the same way and sorted by `claude-haiku-5-5` into Inbox tasks, promises and waiting-on items (`services/connectors/{gmail,slack,sorter,capture}.ts`, details in build plan 12); Claude's email and Slack items are then answered `ignored`. Part C: Drive (`google-drive`) suggests project files for the Library and reads the text of Library Drive documents into `document_contents` (used by Ask, briefs and search); Granola (Personal API key in the `GRANOLA_API_KEY` secret, falling back to the `granola` connector) reads notes from meetings Ollie was in into the Inbox, Knowledge Inbox and briefs (`services/connectors/{drive,granola,meetingCapture}.ts`, details in build plan 12).
- Home Today strip comes from the calendar (read by OllieOS itself once Google Calendar has had a good check, otherwise from the sweep); the Next meeting has Brief me when it has a brief, opening `/briefs/:eventId`. The status line links "Today's digest" once it exists.
- Meetings page (Assist Part B) at `/meetings`, in the desktop rail between Tasks and People; on phones it is in the More sheet (and Home's Today header links to it). Lists work meetings from today to six days ahead by day, with who is coming and readiness (brief state, open promises, items waiting on them), then the last two weeks with a Granola snippet. Meetings with nobody or nothing known, and no one from an outside company domain, have no prep page; they open at `/meetings/:eventId` instead (who is coming with Add to Contacts, and Ollie's agenda and notes). Ollie's notes live on `calendar_events.notes` for every work meeting (`PATCH /api/meetings/:id`, and `PATCH /api/briefs/:id` writes the same column); older notes on `meeting_briefs.notes` are shown until edited, then moved. Your agenda (both pages, `components/meeting-agenda.tsx`): `POST /api/meetings/:id/agenda` sends Ollie's thoughts and the agenda as it stands to the `agenda_writer` agent (`services/meetingAgenda.ts`, Sonnet), which returns a reply and the whole agenda as Markdown in `notes`. The agenda is a Tiptap rich text editor (`components/rich-agenda.tsx`, `@tiptap/markdown`, loaded lazily via `meeting-agenda-lazy.tsx`) that reads and saves Markdown, so plain older notes open as they were and the writer keeps Ollie's formatting; the conversation is kept in `calendar_events.agenda_chat` (`DELETE .../agenda/chat` starts again). It reads like a brief (get_context for visible attendees and projects, rules, open talking points) and sends nothing when the thoughts, agenda or title name something hidden from AI (409). Notes reach AI only this way. One agenda: the prep page has a single Agenda panel; points to raise, the brief's suggested items and what was not covered last time sit above the editor as ideas with Add (`components/agenda-ideas.tsx`, kept apart so the editor stays lazy), and the agenda writer is handed the suggestions and left-overs too. Close the loop (`services/agendaCheck.ts`, agent `agenda_checker`, Haiku in `agendaJudge.ts`): when a Granola note is attached, or on `POST /api/meetings/:id/agenda/check`, each agenda item is marked covered, partly or not covered in `calendar_events.agenda_check` (out of date when the agenda or note changes; never run when the agenda or title names something hidden from AI). From Granola shows the result and leads the prep page once the meeting has ended. Items not covered are offered on the next agenda for the same meeting (`leftoversFor`: same series, or same title with someone in common) until added or dropped (`PUT .../agenda/check/items/:index`). Keeping it: an agenda on a meeting that leaves the calendar window before it starts is parked in `parked_meeting_notes` by `replaceCalendar` and given back when the same `source_ref` returns (90 days); `clearOldCalendar` keeps finished meetings with an agenda or Granola note for a year (others 30 days); the editor saves on leaving the page as well as after a pause. Ollie's thread verdicts outlive their meeting (`calendar_event_id` set null); the matcher's own are cleared. Personal: `PUT /api/meetings/:id/personal` (This is personal on the meeting page, with Undo) sets `personal` with `personal_set_by_ollie`, which calendar checks leave alone and new meetings in the series inherit. On the Meetings list, events with nobody else on them and nothing known are listed as a quiet Just you line per day, unless they have an agenda or Granola notes. Home's Today strip and the digest link meetings without a brief to `/meetings/:id` (Agenda). Granola after the meeting: `attachMeetingNotes` keeps the note on every work meeting (`calendar_events.granola_ref`, `granola_url`, `granola_notes`, `granola_task_ids`, `granola_attached_at`), with or without a brief, and still copies it to the brief when there is one. A note without Granola's calendar link is matched by `findEventForNote`: a work meeting starting within 30 minutes with the same title or someone in common, never one already linked to another note. Both pages show From Granola (`components/from-granola.tsx`) once the meeting ends, with Check Granola now while waiting. Link a note pastes a Granola share or note link (`POST /api/meetings/:id/granola`, `linkGranolaNote` in `services/connectors/index.ts`): the not_ id is fetched directly, a /d/ or /t/ link's UUID is found among notes updated since the meeting; a note already read is only attached (with its tasks), a new one is read in full against the meeting and marked read. Recent email and Slack on prep pages (`services/threadMatch.ts`): up to 20 threads with the people are judged once per meeting by `thread_matcher` (Haiku, `threadJudge.ts`) learning from Ollie's verdicts in `meeting_thread_checks`; Not about this meeting (`PUT /api/meetings/:id/threads/:activityId`) wins, carries to the series and keeps the thread out of the brief writer; hidden threads can be put back. Who's in the room (prep page) and Who's coming (meeting page): names and organisations link to their pages; anyone not in Contacts has Add to Contacts, and Add N to Contacts adds everyone at once in one dialog (`components/add-to-contacts.tsx`; a new organisation shared by several people is created once) with the organisation preselected from `suggestedOrganisation` (`services/orgSuggest.ts`: the organisation most people at the same email domain belong to, the one internal organisation for Ollie's own domain, else a new one named after the domain, created in the same step; nothing for personal addresses). Each meeting is Internal or External (`services/meetingScope.ts`). Prep pages stay at `/briefs/:eventId` (the rail shows Meetings as active there). Bump `BRIEF_VERSION` in the briefs service when the brief gains a model-written section so existing briefs are rewritten.

## Gotchas

- The web build fails when the JavaScript a first page load needs goes over `INITIAL_JS_BUDGET_KB` (gzipped) in `artifacts/ollieos/vite.config.ts`. Lazy-load new pages rather than raising it; raise it only on purpose.
- A sideways-scrolling box needs `position: relative` if anything inside it is absolutely positioned (`sr-only` included), or that element widens the page on phones. Use `ScrollRow` for rows of tabs.
- Phone tap areas come from an invisible `::before` layer (end of `index.css`); give a small one-off link or button the class `oo-tap`, and keep about 10px between small controls. Run `mobile-audit -- --strict` after layout changes: it fails on small targets, small text fields, and controls covered by another's tap layer.
- OllieOS component CSS in `index.css` sits in `@layer components` so Tailwind utilities like `hidden sm:flex` can override it.
